# Deploying the demo

Three builds from one codebase. They differ in what is reachable at the other end of a
button, and each says which one it is.

| | `python3 demo/server.py` | Vercel | GitHub Pages |
|---|---|---|---|
| Compose your own program | live | live | **not offered** |
| Explain / disassemble | live | live | prebaked per example |
| **Run the proof** (`kprove`) | live | replayed `↺` | replayed `↺` |
| **Run for real** (`forge`) | live | replayed `↺` | replayed `↺` |
| Needs a process | yes | one function | **no** |

## GitHub Pages — the fully static build

`./prebake.py` writes `docs/index.html`: one self-contained file, no fetch, no API, no
process. Every answer is computed at bake time by the same `server.py` functions the live
demo calls, for each of the 13 shipped programs, and frozen.

```bash
cd demo && ./record_runs.py && ./prebake.py
```

Then on GitHub: **Settings → Pages → Source: Deploy from a branch → Branch `vk/demo`,
folder `/docs`**. It serves at `https://vovunku.github.io/swap-vm-verified/`.

The playground is deliberately absent rather than present-but-broken. Composing a program
means assembling and checking it, which needs Python; a page that offered the controls and
then failed on submit would be worse than one that does not offer them. What remains is
every shipped example with what the tools actually returned for it — and a footer saying so.

`prebake.py` refuses to run if any recorded proof is not OK, because a page baked from a
broken recording looks exactly like one baked from a good recording.

Tested by `node test/static-page.mjs` (25 checks), which deletes `fetch` and `XMLHttpRequest`
before parsing — so any attempt to reach the network is a hard failure rather than a blank
panel that still photographs well.

## Why the hosted site cannot prove

`/api/prove` shells out to `kprove` inside the `kontrol` container and `/api/execute` shells
out to `forge` (`server.py`, `_kprove` and `execute_live`). A Vercel function has no Docker,
no K, no Foundry, a 250 MB bundle limit against a multi-gigabyte K definition, and a 30 s
ceiling against proofs that run 10 s to 10 min. This is not a packaging problem with a
clever fix — it is a hard limit, and the honest response is to replay runs that really
happened and say so.

`server.LIVE` is `False` when `$VERCEL` is set. Every replayed response carries
`recorded: true`, its timestamp, and the definition fingerprint; the UI prints
`↺ replayed, not live` above it. **Do not remove that label.** A frozen run presented as a
live one is exactly the fake this project argues against.

## Deploy

The repo is already on GitHub, so no CLI is needed:

1. vercel.com → **Add New… → Project** → import `vovunku/swap-vm-verified`
2. **Root Directory: `demo`** ← the only setting that matters
3. Framework preset: **Other**. No build command, no output directory.
4. Deploy.

`demo/vercel.json` does the rest: routes `/api/*` to the single Python function in
`api/index.py`, and `/` to `static/index.html`.

With the CLI instead:

```bash
npm i -g vercel
cd demo && vercel --prod
```

## Refreshing the recordings

`data/runs.json` is generated by really running both tools. It is stale the moment the
semantics change, and a stale recording is a lie with a timestamp on it — so re-record and
re-deploy together:

```bash
cd demo
./record_runs.py              # ~2 min: 4 kprove pairs + 26 forge runs
./record_runs.py --prove      # proofs only, ~40 s
```

It exits non-zero if any spec stopped proving or any negative control started proving, so a
build step can refuse to ship it. It records both states of the "taker holds the gate token"
checkbox for every shipped program, because that is the only input the UI varies.

Requires the `kontrol` container up, with `/home/user/sem2` (K definition) and
`/home/user/fee-work` (Foundry workspace). Override with `DEMO_K_WS`, `DEMO_EXEC_WS`,
`DEMO_EXEC_CONTAINER`.

## Making the hosted site prove for real

Point it at a machine that can. Set `DEMO_BACKEND` in Vercel's environment to the base URL
of another copy of this server running with `DEMO_LIVE=1`:

```bash
# on the box with the container
DEMO_LIVE=1 python3 demo/server.py
cloudflared tunnel --url http://localhost:8000
# then in Vercel: DEMO_BACKEND=https://<whatever>.trycloudflare.com
```

`prove` and `execute` forward there with a 25 s timeout. If it is unreachable they fall
back to the recording rather than erroring — a labelled replay beats a demo that dies when
the wifi does.

## What is NOT deployed

The proofs themselves. `demo/` is a viewer; the claims live in `semantics/proofs/*.k` and
`../dustproof/semantics/*.k`, and the way to check them is to run them:

```bash
./semantics/run-proofs.sh              # swap-vm-verified
../dustproof/semantics/run-proofs.sh   # DustProof: D1 + its negative control
```

See `VERIFY.md`. Nothing in the hosted demo is evidence of anything the repo cannot
reproduce on your own machine.
